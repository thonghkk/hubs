01
Process, Application & Zygote
OS Foundation — trước khi học component, phải hiểu chúng sống ở đâu và chết khi nào

Mỗi Android app chạy trong một Linux process riêng biệt với UID duy nhất — đây là sandbox security cơ bản. Process được fork từ Zygote sử dụng cơ chế Copy-on-Write (COW): Zygote đã pre-load toàn bộ Android framework classes, nên khi fork app mới, child process kế thừa pages bộ nhớ này mà không cần copy vật lý — tiết kiệm RAM và thời gian khởi động.

TaskStack của Activity theo luồng userCó thể span nhiều process
Back StackActivity stack trong một TaskNavigation history

ApplicationSingleton sống cùng processKhông safe cho UI state

⚠️

Process Importance Hierarchy

Foreground (oom=-1000) → Visible (oom=-800) → Service (oom=0) → Cached/Background (oom=900+). LMKD kill từ oom cao nhất khi RAM thấp.

🔴

Process Death — không báo trước

OS kill process không gọi onDestroy(). Singleton, static var, ViewModel — tất cả mất. Chỉ SavedStateHandle và DB tồn tại.

Kotlin
class CoreApplication : Application() {

    override fun onCreate() {
        super.onCreate()
        // Chỉ khởi tạo những gì THỰC SỰ cần ngay
        // SDK nặng → lazy/async init để không block cold start
        initCriticalSdks()

        // Async init — không block Application.onCreate()
        ProcessLifecycleOwner.get().lifecycle
            .addObserver(AppLifecycleObserver())
    }

    /**
     * Gọi khi hệ thống cần app giải phóng memory.
     * KHÔNG bao giờ gọi khi normal exit.
     */
    override fun onTrimMemory(level: Int) {
        super.onTrimMemory(level)
        when (level) {
            ComponentCallbacks2.TRIM_MEMORY_UI_HIDDEN -> {
                // App vào background — giải phóng UI caches
                imageCache.clear()
            }
            ComponentCallbacks2.TRIM_MEMORY_RUNNING_CRITICAL,
            ComponentCallbacks2.TRIM_MEMORY_COMPLETE -> {
                // RAM nghiêm trọng — giải phóng mọi thứ có thể
                clearAllCaches()
            }
        }
    }
}
🚫

Đừng giả định process tồn tại liên tục

Thiết kế state recovery cho mọi màn hình. Process có thể bị kill bất cứ lúc nào khi app ở background — kể cả sau vài giây.

⚡

Application.onCreate() không phải entry point duy nhất

ContentProvider.onCreate() được gọi TRƯỚC Application.onCreate(). Nếu dùng ContentProvider để init SDK, cẩn thận circular dependency.

✅

Phân loại data theo scope

Transient UI state → SavedStateHandle. Session data → ViewModel. Critical data → Room/DataStore. Không trộn lẫn.

🔬

Zygote vs traditional spawn

Zygote pre-loads ~50MB ART bytecode. Fork COW = cold start <100ms thay vì >1s nếu spawn từ đầu. Trade-off: memory fragmentation nếu nhiều process.

Q
Điều gì xảy ra khi người dùng nhấn vào icon ứng dụng?
▶

Launcher gửi startActivity() Intent → Binder IPC tới System Server (AMS/ATMS) → AMS kiểm tra process đã tồn tại chưa → Nếu chưa: AMS gửi lệnh tới Zygote qua socket (/dev/socket/zygote) → Zygote fork() process mới với COW → child process chạy ActivityThread.main() → khởi tạo Looper → gửi Binder message "process ready" về AMS → AMS dispatch handleLaunchActivity → Application.onCreate() → Activity.onCreate().

Q
Tại sao Android dùng Zygote thay vì spawn process trực tiếp?
▶

Zygote pre-load toàn bộ Android framework classes, ART runtime và shared libraries vào memory trước. Khi fork app mới, child process kế thừa các memory pages này qua Copy-on-Write — không cần copy vật lý, tiết kiệm ~50MB RAM per process và giảm cold start từ >1s xuống <100ms. Nếu spawn từ đầu, mỗi app phải load lại toàn bộ framework.

Q
Tại sao singleton không an toàn để lưu UI state?
▶

Singleton sống trong process memory. Khi process bị kill (không có callback, không có cảnh báo), toàn bộ singleton state mất sạch. Khi user quay lại app (tưởng app vẫn mở), hệ thống tạo process mới — singleton reset về trạng thái ban đầu. UI state phải được lưu qua cơ chế có persistence: onSaveInstanceState → SavedStateHandle → Room/DataStore.

Q
Process death khác configuration change thế nào?
▶

Configuration change: Activity bị destroy + recreate nhưng process VẪN sống → ViewModel sống sót qua NonConfigurationInstances → chỉ cần lưu UI state nhỏ qua onSaveInstanceState.

Process death: Toàn bộ process bị kill → mọi thứ trong RAM mất → ViewModel, singleton, static vars đều mất → phục hồi cần SavedStateHandle (Bundle nhỏ) + Room/DataStore (data quan trọng).

Q
Android kill process khi nào và process nào bị kill trước?
▶

Low Memory Killer Daemon (LMKD) quyết định dựa trên oom_score_adj: Foreground (-1000) → gần như không bao giờ bị kill. Visible (-800) → hiếm. Service Process (0-200) → bị kill khi RAM thấp. Cached/Background (900-1000) → bị kill đầu tiên. Process có score cao nhất bị kill trước. Foreground Service có oom_adj ~200, vẫn có thể bị kill khi memory cực thấp.

Q
Application.onCreate() có luôn gọi trước Activity.onCreate() không?
▶

Thường là vậy — nhưng có ngoại lệ quan trọng: ContentProvider.onCreate() được gọi TRƯỚC Application.onCreate(). Nếu ContentProvider của bạn cần dùng thứ gì đó từ Application, bạn sẽ gặp NPE. Ngoài ra, khi app bị kill và user quay lại qua deep link/notification, Activity được restore — Application.onCreate() vẫn chạy trước vì process mới.

02
Main Thread, Looper, MessageQueue & Handler
Event loop dựa trên Linux epoll — nền tảng của ANR, lifecycle và coroutine dispatcher

Main thread dùng mô hình single-threaded event loop. ViewRootImpl.checkThread() enforce rằng chỉ thread tạo View mới được cập nhật nó — không phải vì thread-safety mà vì draw order và invalidation correctness. Looper không chiếm CPU khi rảnh — nó block trên Linux epoll (nativePollOnce) cho đến khi có message mới.


Thành phầnVai tròGhi chú quan trọng
LooperQuản lý event loop cho một thread1 thread = tối đa 1 Looper (ThreadLocal)
MessageQueuePriority linked list, sort by "when"Sync barrier cho VSYNC/Choreographer
HandlerPost message/runnable vào queueGiữ tham chiếu outer class → memory leak
MessageContainer dữ liệu được queuePool recycling, dùng obtainMessage()

🔴

ANR Timeouts

Input event không xử lý trong 5 giây → ANR. BroadcastReceiver không complete trong 10 giây (foreground) / 60 giây (background). Service không respond trong 20 giây (foreground) / 200 giây (background).

Thread.main()
↓
Looper.prepare() — tạo MessageQueue, lưu vào ThreadLocal
↓
Looper.loop() — vòng lặp vô tận for(;;)
↓
MessageQueue.next() — nativePollOnce(epoll_wait)
↓ block đến khi có message
Message đến — nativeWake() thức dậy epoll
↓
msg.target.dispatchMessage() — Handler callback
↓ quay lại next()

💡

Tại sao Looper.loop() không ngốn CPU?

MessageQueue.next() gọi nativePollOnce(fd, timeout) — block trên Linux epoll_wait. Thread ngủ ở kernel level, không chiếm CPU đến 0ms wakeup time. Khi Handler.post() gọi nativeWake(), kernel đánh thức thread ngay lập tức.

Kotlin — Memory-safe Handler
// ❌ ANTI-PATTERN: Handler giữ Activity reference qua delayed message
class BadActivity : AppCompatActivity() {
    private val handler = Handler(Looper.getMainLooper()) {
        // 'this@BadActivity' bị giữ trong closure
        updateUI() // memory leak nếu delay > Activity lifetime
        true
    }
}

// ✅ CORRECT: WeakReference + lifecycle-aware cancellation
class SafeHandler(activity: Activity) : Handler(Looper.getMainLooper()) {
    private val weakRef = WeakReference(activity)

    override fun handleMessage(msg: Message) {
        weakRef.get()?.run {
            // Activity đã GC nếu null — bỏ qua message
            updateUI()
        }
    }
}

// ✅ BETTER (Modern): Coroutine thay Handler
class ModernActivity : AppCompatActivity() {
    private fun scheduleUiUpdate() {
        lifecycleScope.launch {
            delay(1000L) // auto-cancelled khi lifecycle DESTROYED
            updateUI()
        }
    }
}

// HandlerThread: dedicated Looper thread cho background work
val workerThread = HandlerThread("WorkerThread")
workerThread.start()
val backgroundHandler = Handler(workerThread.looper)
backgroundHandler.post { /* heavy work, NOT on main thread */ }
⚠️

suspend ≠ background execution

suspend fun chỉ có thể suspend, không guarantee chạy trên background thread. withContext(Dispatchers.IO) mới đổi thread. Dispatchers.Main dùng Handler nội bộ — vẫn là main thread.

🔴

Synchronization Barrier ẩn

VSYNC signal đặt sync barrier vào MessageQueue — block tất cả synchronous messages, chỉ async messages (Choreographer) đi qua. Nếu bạn delay xử lý async message, frame drop xảy ra.

✅

Coroutine vs Handler

Handler: low-level, cần manual lifecycle management. Coroutine: structured concurrency, tự cancel theo lifecycle, structured error handling. Dùng Coroutine cho mọi async work mới.

🔬

GC Root chain

Looper → MessageQueue → Message → Message.target (Handler) → Handler inner class → Activity. Delayed message giữ chain này sống. Activity bị destroy nhưng không thể GC.

Q
Looper hoạt động như thế nào? Tại sao một thread không tự có Looper?
▶

Looper là event loop manager cho một thread. Cần gọi Looper.prepare() để tạo Looper + MessageQueue và lưu vào ThreadLocal, sau đó Looper.loop() để bắt đầu vòng lặp. Thread mới không có Looper vì tạo Looper là tốn tài nguyên — chỉ thread cần xử lý messages mới tạo. Main thread được Android setup sẵn Looper trong ActivityThread.main().

Q
Tại sao không được cập nhật View từ background thread?
▶

ViewRootImpl.checkThread() verify thread identity và throw CalledFromWrongThreadException nếu không phải thread tạo ViewRootImpl (luôn là main thread). Lý do: View invalidation, drawing pass và layout không thread-safe — nếu nhiều thread cập nhật đồng thời, draw order bị corrupt, dẫn đến visual glitch hoặc crash.

Q
Coroutine có thay thế hoàn toàn Handler không?
▶

Gần như vậy cho app-level code, nhưng không hoàn toàn. Dispatchers.Main thực ra dùng Handler nội bộ để dispatch coroutine resumption về main thread. Handler vẫn cần ở framework level, view system internals và một số interop với Java code cũ. Với Kotlin app code mới, Coroutine + Flow là lựa chọn tốt hơn Handler vì structured concurrency và lifecycle-awareness.

Q
Handler.post() thực sự làm gì bên dưới?
▶

Handler.post(Runnable) → tạo Message.obtain() với callback = runnable → sendMessageDelayed(msg, 0) → MessageQueue.enqueueMessage(msg, when) → sort vào priority queue theo when (SystemClock.uptimeMillis) → nativeWake() nếu queue đang ngủ → epoll wakeup → dispatchMessage() → handleCallback(msg) → msg.callback.run().

Deep Link & Synthetic Back Stack

Dùng TaskStackBuilder để tạo back stack tự nhiên khi user đến từ notification/deep link. Không làm: user nhấn Back → thoát app thay vì về màn hình trước.

Q
Khi xoay màn hình, callback nào được gọi?
▶

onPause() → onStop() → onSaveInstanceState() → onDestroy() [activity cũ bị destroy] → onCreate(savedState) → onStart() → onRestoreInstanceState(savedState) → onResume() [activity mới]. ViewModel KHÔNG bị destroy — được truyền qua NonConfigurationInstances trong ActivityThread.

Q
ViewModel có sống qua process death không?
▶

Không. ViewModel sống trong process memory, chỉ survive qua configuration change nhờ ViewModelStore được giữ trong NonConfigurationInstances. Khi process bị kill, mọi thứ trong RAM mất — ViewModel cũng vậy. Để survive process death, phải dùng SavedStateHandle (serialize vào Bundle) hoặc Room/DataStore.

Q
onSaveInstanceState() nên lưu loại dữ liệu nào?
▶

Chỉ lưu lightweight UI state nhỏ: selected tab index, scroll position, text field content, navigation args. Không lưu: large objects, bitmaps, lists dài. Bundle được serialize/deserialize qua Binder (giới hạn ~1MB tổng), lưu quá nhiều → TransactionTooLargeException. Data lớn → Room/DataStore.

Q
singleTop, singleTask và singleInstance khác nhau thế nào?
▶

singleTop: Nếu instance đang ở TOP của back stack, reuse và gọi onNewIntent() — không tạo mới. Nếu không ở top, vẫn tạo mới.
singleTask: Chỉ tồn tại 1 instance trong task. Nếu đã tồn tại ở bất kỳ vị trí nào trong stack, clear mọi Activity phía trên nó và gọi onNewIntent().
singleInstance: Như singleTask nhưng task riêng biệt, không có Activity nào khác trong cùng task.

// ✅ ViewBinding safe cleanup — tránh memory leak
class SafeFragment : Fragment(R.layout.fragment_safe) {
    private var _binding: FragmentSafeBinding? = null
    private val binding get() = _binding!!

    override fun onViewCreated(view: View, savedInstanceState: Bundle?) {
        _binding = FragmentSafeBinding.bind(view)

        // ✅ viewLifecycleOwner — cancel khi view destroyed
        viewLifecycleOwner.lifecycleScope.launch {
            viewLifecycleOwner.repeatOnLifecycle(Lifecycle.State.STARTED) {
                viewModel.uiState.collect { state ->
                    render(state)
                }
            }
        }
    }

    // ✅ Bắt buộc null binding ở đây — không ở onDestroy()
    override fun onDestroyView() {
        super.onDestroyView()
        _binding = null // View đã bị GC, không giữ reference
    }
}

Q
Vì sao Fragment có hai lifecycle? Khi nào viewLifecycleOwner quan trọng?
▶

Fragment instance có thể tồn tại lâu hơn View của nó (ví dụ khi replace + addToBackStack). View bị destroy trong onDestroyView() nhưng Fragment vẫn trong back stack. Nếu observe LiveData với Fragment lifecycle → observer sống sót khi View không còn → khi navigate lại, Fragment recreate view + observer mới → hai observers collect cùng lúc. Dùng viewLifecycleOwner → observer tự cancel khi onDestroyView().

Q
Tại sao giữ ViewBinding sau onDestroyView() gây memory leak?
▶

ViewBinding giữ strong reference đến tất cả Views trong layout. Khi onDestroyView() được gọi, Fragment detach View khỏi window và muốn GC View hierarchy. Nhưng nếu Fragment field _binding vẫn non-null → binding vẫn giữ View references → toàn bộ View hierarchy + Bitmap resources không thể GC → OOM risk khi navigate nhiều lần. Fix: _binding = null trong onDestroyView().

Q
commit() vs commitAllowingStateLoss() — khi nào dùng cái nào?
▶

commit() throw IllegalStateException nếu gọi sau onSaveInstanceState() — để bảo vệ: transaction sẽ bị mất sau restore. commitAllowingStateLoss() cho phép commit bất cứ lúc nhưng transaction có thể mất nếu Activity bị recreate ngay sau đó. Dùng commit() khi có thể, commitAllowingStateLoss() chỉ cho UI-only operations không quan trọng (như dismiss dialog từ background callback).

05
Intent & Intent Filter
Message object kích hoạt component — resolution algorithm, Parcelable và Binder transaction limit
✅

Explicit Intent

Chỉ định component trực tiếp: Intent(context, TargetActivity::class.java). Không cần Intent Filter. An toàn, nhanh, không bị chặn bởi background limits.

🔍

Implicit Intent Resolution

AMS hỏi PackageManager → duyệt IntentFilter của tất cả app: (1) Action test (2) Category test (3) Data/MIME test. Tất cả pass → match. Nhiều match → Chooser dialog.

⚠️

Binder Transaction Limit ~1MB

Đây là tổng buffer cho TOÀN BỘ process, không phải per-call. Truyền Bitmap/List lớn qua Intent extras → TransactionTooLargeException. Giải pháp: lưu vào Room/file → truyền ID.

🔗

App Link vs Deep Link

Deep link: custom scheme (myapp://), không verified, có thể bị hijack. App Link (Android 6.0+): HTTPS + autoVerify="true" + assetlinks.json → verified, mở trực tiếp không qua chooser.

Q
Hệ thống resolve Implicit Intent như thế nào?
▶

PackageManagerService duyệt tất cả IntentFilter đã register (manifest + runtime). Mỗi filter phải pass 3 tests: (1) Action test: Intent action phải có trong filter. (2) Category test: Mọi category trong Intent phải có trong filter (filter có thể có thêm). (3) Data test: URI scheme, host, path và MIME type phải match. Nếu nhiều kết quả → app chooser. Q
Tại sao Parcelable nhanh hơn Serializable?
▶

Serializable dùng Java reflection để khám phá fields tại runtime — chậm và tạo nhiều temporary objects. Parcelable yêu cầu developer viết marshaling code thủ công (hoặc dùng @Parcelize compiler plugin) → ghi trực tiếp vào native C++ Parcel buffer, không reflection, không GC pressure. Parcelable ~10x nhanh hơn trên Android benchmark.

PendingIntent
System-level token — tồn tại sau process death, trao quyền cho hệ thống thực thi Intent thay mặt app

PendingIntent là IIntentSender token được lưu trong system_server memory (AMS). Token này mang theo: Intent, app identity (UID), type (Activity/Service/Broadcast). Khi hệ thống kích hoạt PendingIntent, nó dùng quyền hạn của app creator — không phải của app kích hoạt. Đó là lý do nó hoạt động kể cả khi app process đã chết.

⚠️

Hai PendingIntent "giống nhau" khi nào?

Hệ thống so sánh bằng Intent.filterEquals(): Action, Data, Type, Package, Component và Categories. Extras KHÔNG được so sánh (trước Android 12). requestCode khác nhau → PendingIntent khác nhau.

🔴

Android 12 — Bắt buộc FLAG_IMMUTABLE hoặc FLAG_MUTABLE

Không khai báo flag → crash SecurityException. Ưu tiên FLAG_IMMUTABLE cho hầu hết trường hợp. Chỉ dùng FLAG_MUTABLE khi cần đối tác (AlarmManager, Notification Direct Reply) cập nhật Intent.

Q
Tại sao PendingIntent hoạt động khi app process đã chết?
▶

PendingIntent là system-level token (IIntentSender) được lưu trong System Server memory (AMS), không phải app memory. Token này chứa app's UID và Intent data. Khi hệ thống kích hoạt, nó dùng quyền của app creator để launch component — không cần app process tồn tại. Nếu process cần được launch, hệ thống fork process mới trước.

Q
Security risk nào với PendingIntent mutable?
▶

Intent Redirection attack: Nếu trao FLAG_MUTABLE PendingIntent cho một app độc hại, app đó có thể thay đổi component/data trong Intent → kích hoạt component nhạy cảm với quyền của app victim. Ví dụ: thay đổi Intent để launch exported Activity với elevated privilege. Luôn dùng FLAG_IMMUTABLE + Explicit Intent trong PendingIntent khi không cần đối tác modify.

onReceive() phải hoàn thành nhanh

Chạy trên Main Thread. Timeout: ~10 giây (foreground), ~60 giây (background). Sau khi return, process có thể bị kill ngay lập tức. Không làm: network call, database write, bất kỳ async work nào mà không dùng goAsync().

Kotlin — goAsync() với Coroutine
class BootReceiver : BroadcastReceiver() {
    override fun onReceive(context: Context, intent: Intent) {
        if (intent.action != Intent.ACTION_BOOT_COMPLETED) return

        // ✅ Chỉ validate + schedule — không làm nặng ở đây
        WorkManager.getInstance(context)
            .enqueueUniqueWork(
                "sync_after_boot",
                ExistingWorkPolicy.KEEP,
                OneTimeWorkRequestBuilder<SyncWorker>()
                    .setConstraints(
                        Constraints.Builder()
                            .setRequiredNetworkType(NetworkType.CONNECTED)
                            .build()
                    ).build()
            )
    }
}

// goAsync() pattern — khi cần thêm thời gian (dùng thận trọng)
class AsyncReceiver : BroadcastReceiver() {
    private val scope = CoroutineScope(SupervisorJob())

    override fun onReceive(context: Context, intent: Intent) {
        val pendingResult = goAsync() // Kéo dài thời gian sống
        scope.launch {
            try {
                doQuickWork() // Phải hoàn thành trong 10s
            } finally {
                pendingResult.finish() // BẮT BUỘC gọi để giải phóng
            }
        }
    }
}
Q
Điều gì xảy ra với process sau khi onReceive() return?
▶

Sau khi onReceive() return, nếu không có component nào khác đang chạy, hệ thống có thể kill process ngay lập tức. Đây là lý do không được start async work (Thread, AsyncTask) trong onReceive() — thread sẽ bị cut off. Nếu cần async: dùng goAsync() hoặc schedule WorkManager/JobScheduler.

Q
Tại sao Android 8.0+ cấm hầu hết implicit broadcast trong Manifest?
▶

Thundering Herd Problem: Trước API 26, khi system broadcast như CONNECTIVITY_CHANGE được gửi, hàng chục app cùng có static receiver → hệ thống fork đồng loạt hàng chục process → CPU spike, RAM exhaustion, LMK dọn dẹp các app khác, pin tụt nhanh. Google cấm implicit broadcast với static receiver từ API 26 để giải quyết vấn đề này. Exception: BOOT_COMPLETED, MY_PACKAGE_REPLACED, LOCALE_CHANGED vẫn được phép.

✅

Music playback, navigation, workout tracking, ongoing upload. Bắt buộc: persistent notification, startForeground() trong 5-10 giây sau start, foreground service type từ Android 10+.

🚫

Không phải Foreground Service

Upload log có thể trì hoãn, sync định kỳ, cleanup task. Dùng WorkManager thay thế. FGS là để work USER NHẬN BIẾT — không phải để lách background limits.

🔬

Vẫn có thể bị kill

Kotlin — Foreground Service với LifecycleService
@AndroidEntryPoint
class TrackingService : LifecycleService() {
    @Inject lateinit var tracker: LocationTracker

    // ✅ Scope gắn với Service lifecycle
    private val serviceScope = CoroutineScope(
        SupervisorJob() + Dispatchers.Default
    )

    override fun onCreate() {
        super.onCreate()
        startForeground(NOTIFICATION_ID, buildNotification())
        serviceScope.launch {
            tracker.locationFlow.collect { location ->
                updateNotification(location)
            }
        }
    }

    override fun onDestroy() {
        super.onDestroy()
        serviceScope.cancel() // ✅ Cancel tất cả coroutines
    }
}
Q
Service có thread riêng không?
▶

Không. Service callback (onCreate, onStartCommand, onBind, onDestroy) đều chạy trên Main Thread của hosting process. Đây là lỗi hiểu nhầm phổ biến nhất. Nếu làm việc nặng trong Service (network, file I/O, heavy computation), phải tự tạo background thread/coroutine — ví dụ dùng CoroutineScope(Dispatchers.IO) trong Service.

Q
Tại sao Foreground Service vẫn có thể bị kill?
▶

Foreground Service có oom_score_adj ~200, cao hơn normal service (~500) và background app (~900) nhưng không immortal. Khi RAM cực kỳ thấp, LMKD vẫn kill Foreground Service. Ngoài ra, user có thể force-stop app, hoặc hệ thống có thể kill vì battery optimization. "Foreground" nghĩa là user-visible và higher priority — không phải bất tử.

09
WorkManager
Guaranteed ≠ Immediate — deferred work với persistence, constraints và idempotency
✅

Khi nào dùng WorkManager

Upload log/content, sync dữ liệu, cleanup định kỳ, retry sau mất mạng, compress file. Tiêu chí: có thể trì hoãn + cần đảm bảo thực thi kể cả sau restart.

🚫

KHÔNG dùng WorkManager

Music playback (Foreground Service), real-time tracking (Foreground Service), exact alarm (AlarmManager), work cần chạy ngay lập tức với latency thấp.

⚠️

Guaranteed ≠ Immediate

WorkManager dùng JobScheduler/AlarmManager + Doze mode batching. Constraint chưa thỏa mãn → work chờ. Doze mode → batch delay. Periodic work minimum interval = 15 phút.

🔬

Internals: Room-backed

WorkDatabase (Room) lưu mọi work request. Khi process bị kill, RescheduleReceiver nhận BOOT_COMPLETED → reschedule từ DB. Đây là cơ chế "guaranteed".

Kotlin — CoroutineWorker + Unique Work
// ✅ Idempotent Worker — safe to retry nhiều lần
class SyncWorker(ctx: Context, params: WorkerParameters) :
    CoroutineWorker(ctx, params) {

    override suspend fun doWork(): Result {
        return try {
            setProgress(workDataOf("progress" to 0))
            val items = repository.getPendingItems()

            items.forEachIndexed { index, item ->
                repository.syncItem(item) // Idempotent: check server first
                setProgress(workDataOf(
                    "progress" to ((index + 1) * 100 / items.size)
                ))
            }

            Result.success()
        } catch (e: IOException) {
            if (runAttemptCount < 3) Result.retry()
            else Result.failure()
        }
    }
}

// Unique work — tránh duplicate
WorkManager.getInstance(ctx)
    .enqueueUniqueWork(
        "sync",
        ExistingWorkPolicy.KEEP, // Giữ work đang chạy, không thêm mới
        OneTimeWorkRequestBuilder<SyncWorker>()
            .setConstraints(
                Constraints(requiredNetworkType = NetworkType.CONNECTED)
            )
            .setBackoffCriteria(BackoffPolicy.EXPONENTIAL, 30, TimeUnit.SECONDS)
            .build()
    )
Q
Tại sao Worker phải idempotent?
▶

WorkManager có thể retry Worker nhiều lần: do network failure, constraint violated mid-execution, process killed. Nếu Worker không idempotent → mỗi retry tạo duplicate effects (upload 2 lần, insert 2 bản ghi). Thiết kế idempotent: check server/DB trước khi write, dùng UPSERT thay INSERT, unique constraint trong DB, idempotency key cho API calls.

Q
Khi process bị kill, work được phục hồi thế nào?
▶

WorkManager persist mọi work request vào WorkDatabase (Room). WorkManager đăng ký RescheduleReceiver để nhận ACTION_BOOT_COMPLETED và các events khác. Khi device restart hoặc process được recreate, WorkManager đọc từ DB và reschedule với JobScheduler/AlarmManager. Work ở trạng thái RUNNING/ENQUEUED được reset về ENQUEUED và reschedule.

Phía provider: CRUD methods (query, insert, update, delete) chạy trên Binder thread pool (max 16 threads) — có thể concurrent. onCreate() chạy trên main thread của provider process.

Binder IPC
Android's core IPC — 1-copy via mmap, Proxy/Stub pattern, thread pool và security boundary
Client App — method call trên Proxy
↓ marshal vào Parcel

↓
Stub.onTransact() → unmarshal Parcel

Client unblocked (synchronous) hoặc không block (oneway)

🔬

Tại sao Binder nhanh hơn Socket/Pipe?

Socket/Pipe: 2 copies (user→kernel, kernel→user). Binder: 1 copy — kernel mmap ánh xạ physical pages trực tiếp vào user space của server. Cộng thêm: identity verification ở kernel level (không thể spoof UID/PID).

⚠️

Transaction size limit ~1MB

Buffer TOÀN BỘ process, không per-call. Nếu nhiều concurrent Binder calls → dễ vượt limit → TransactionTooLargeException. Không truyền Bitmap/large List qua Binder — dùng file + URI.

⚠️

Synchronous Binder call trên Main Thread

Binder call đồng bộ block thread gọi cho đến khi server return. Nếu server chậm (database, network, deadlock) → main thread block → ANR sau 5 giây. Luôn async hoặc gọi từ background thread.

🔐

Security: kernel-verified identity

Binder.getCallingUid() và Binder.getCallingPid() được kernel xác thực — không thể spoof. Server có thể verify caller identity và reject unauthorized calls. Cơ sở cho toàn bộ Android permission system.

🔬

DeathRecipient

linkToDeath() đăng ký callback được gọi khi remote process chết. Quan trọng cho bound service client: cleanup state, reconnect hoặc notify user khi service process crash.

Q
Binder giải quyết vấn đề gì so với IPC truyền thống?
▶

Socket/Pipe: 2 memory copies, không có identity, không có security. Shared memory: 0 copy nhưng cần external sync, không có identity. Binder giải quyết: (1) 1 copy qua mmap — hiệu quả. (2) Kernel-verified identity (UID/PID) — security. (3) Object-oriented RPC — dễ dùng hơn raw bytes. (4) Reference counting — automatic cleanup khi client disconnect.

Q
Tại sao một API trông như local method call có thể là IPC?
▶

Binder Proxy pattern làm cho IPC call trông giống local call: locationManager.getLastLocation() trông như local call nhưng thực ra là Binder IPC tới LocationManagerService trong System Server process. Implication: call này có thể (1) block nếu server busy, (2) fail với RemoteException nếu server crash, (3) có serialization cost, (4) bị security check. Senior developer phải biết API nào là Binder call để avoid main thread blocking.

Q

ATMS tập trung vào: Activity/Task/back stack management, window transitions, display management. Phân chia SRP — dễ maintain và test hơn.

🧠 7 Lỗi tư duy thường gặp

Những sai lầm phổ biến nhất trong phỏng vấn Senior Android

❌ Sai: Service là background thread

Service callback mặc định chạy trên Main Thread của process.

✅ Đúng

Phải tạo CoroutineScope hoặc Thread riêng trong Service để chạy background work.

❌ Sai: WorkManager luôn chạy ngay

WorkManager dành cho work có thể trì hoãn, bị ảnh hưởng bởi Doze và constraints.

✅ Đúng

"Guaranteed execution" ≠ immediate. Min interval PeriodicWork = 15 phút.

❌ Sai: Foreground Service không bao giờ bị kill

FGS có priority cao hơn nhưng vẫn có thể bị LMKD kill khi memory cực thấp.

✅ Đúng

oom_score_adj ~200 — cao hơn service process nhưng không immortal. Thiết kế để resume được.

❌ Sai: ViewModel sống qua process death

ViewModel chỉ survive configuration change, không phải process death.

✅ Đúng

Process death → mọi thứ trong RAM mất. Dùng SavedStateHandle + Room cho critical data.

❌ Sai: BroadcastReceiver phù hợp cho task dài

onReceive() phải hoàn thành nhanh (10s), không async.

✅ Đúng

Receiver chỉ validate event và schedule WorkManager. goAsync() chỉ cho work ngắn hạn.

❌ Sai: ContentProvider luôn cần thiết khi dùng Room

Provider chủ yếu có giá trị khi chia sẻ data cross-app theo contract.

✅ Đúng

Data nội bộ → Repository + Room. ContentProvider chỉ khi cần cross-app CRUD interface.

❌ Sai: API framework luôn là local call

getSystemService() → nhiều method là Binder IPC tới System Server.

✅ Đúng

LocationManager, ConnectivityManager... → Binder call. Có thể block, throw RemoteException, có security check.
